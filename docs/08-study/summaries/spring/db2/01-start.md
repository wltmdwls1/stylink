## 전체 흐름 한눈에 보기

```
데이터 접근 기술 2가지 분류
  SQL Mapper: JdbcTemplate, MyBatis → SQL 직접 작성, 반복 제거
  ORM:       JPA/Hibernate, 스프링 데이터 JPA, Querydsl → SQL 자동 생성

공통 구조 (각 기술 실습에서 계속 사용)
  ItemRepository 인터페이스 → 구현체만 교체하면 서비스 코드 무변경
  ItemSearchCond (검색 조건), ItemUpdateDto (수정용)
  MemoryItemRepository → JDBC/JPA 구현체로 교체

프로필
  main: spring.profiles.active=local → TestDataInit 빈 등록 (초기 데이터)
  test: spring.profiles.active=test  → TestDataInit 빈 미등록
  @EventListener(ApplicationReadyEvent) 사용 → AOP 포함 완전 초기화 후 호출
```

## 데이터 접근 기술 비교

| 분류 | 기술 | 특징 |
|------|------|------|
| **SQL Mapper** | JdbcTemplate | JDBC 반복 코드 제거, SQL 직접 작성 |
| **SQL Mapper** | MyBatis | XML 또는 어노테이션 기반 SQL, 동적 쿼리 강점 |
| **ORM** | JPA / Hibernate | SQL 자동 생성, 객체-테이블 매핑 |
| **ORM** | 스프링 데이터 JPA | JPA 기반, 메서드 이름으로 쿼리 자동 생성 |
| **ORM** | Querydsl | 타입 안전한 동적 쿼리, JPA와 함께 사용 |

> 실무: JPA + 스프링 데이터 JPA + Querydsl 조합 사용 (거의 필수)

## 프로젝트 공통 구조

### Item 도메인

```java
@Data
public class Item {
    private Long id;
    private String itemName;
    private Integer price;
    private Integer quantity;
}
```

### ItemRepository 인터페이스

```java
public interface ItemRepository {
    Item save(Item item);
    void update(Long itemId, ItemUpdateDto updateParam);
    Optional<Item> findById(Long id);
    List<Item> findAll(ItemSearchCond cond);  // LIKE 검색 포함
}
```

### ItemSearchCond / ItemUpdateDto

```java
@Data
public class ItemSearchCond {
    private String itemName;   // LIKE 검색
    private Integer maxPrice;  // 이하 가격 필터
}

@Data
public class ItemUpdateDto {
    private String itemName;
    private Integer price;
    private Integer quantity;
}
```

> DTO: 데이터 전달 전용 객체. 기능 없이 데이터만 보유. 이름 규칙: `Cond`(검색 조건), `Dto`(수정 등 전달용)

### MemoryItemRepository

```java
@Repository
public class MemoryItemRepository implements ItemRepository {
    private static final Map<Long, Item> store = new HashMap<>();
    private static long sequence = 0L;

    @Override
    public Item save(Item item) {
        item.setId(++sequence);
        store.put(item.getId(), item);
        return item;
    }

    @Override
    public List<Item> findAll(ItemSearchCond cond) {
        return store.values().stream()
                .filter(item -> ObjectUtils.isEmpty(cond.getItemName())
                        || item.getItemName().contains(cond.getItemName()))
                .filter(item -> cond.getMaxPrice() == null
                        || item.getPrice() <= cond.getMaxPrice())
                .collect(Collectors.toList());
    }
}
```

## 설정 구조

### MemoryConfig — 수동 빈 등록

```java
@Configuration
public class MemoryConfig {
    @Bean
    public ItemService itemService() { return new ItemServiceV1(itemRepository()); }
    @Bean
    public ItemRepository itemRepository() { return new MemoryItemRepository(); }
}
```

> 서비스/리포지토리는 수동 등록 (구현체 교체 용이), 컨트롤러는 컴포넌트 스캔.

### ItemServiceApplication — @Import로 설정 선택

```java
@Import(MemoryConfig.class)  // 기술 변경 시 이 부분만 교체
@SpringBootApplication(scanBasePackages = "hello.itemservice.web")
public class ItemServiceApplication {
    @Bean
    @Profile("local")
    public TestDataInit testDataInit(ItemRepository itemRepository) {
        return new TestDataInit(itemRepository);
    }
}
```

## 프로필 설정

### main 프로필 (로컬 실행)

```properties
# src/main/resources/application.properties
spring.profiles.active=local
```

→ `@Profile("local")` 조건 만족 → `TestDataInit` 빈 등록 → 초기 데이터 2건 저장

### test 프로필 (테스트 실행)

```properties
# src/test/resources/application.properties
spring.profiles.active=test
```

→ `@Profile("local")` 조건 불만족 → `TestDataInit` 빈 미등록 → 초기 데이터 없음 (테스트 격리)

### @EventListener(ApplicationReadyEvent) vs @PostConstruct

```java
@EventListener(ApplicationReadyEvent.class)
public void initData() {
    itemRepository.save(new Item("itemA", 10000, 10));
}
```

> `@PostConstruct`: AOP(@Transactional 등)가 아직 적용 안 된 상태에서 호출될 수 있어 문제 가능성.  
> `@EventListener(ApplicationReadyEvent.class)`: 스프링 컨테이너 완전 초기화 후 호출 → 안전.

## 데이터베이스 테이블 생성

```sql
drop table if exists item CASCADE;
create table item (
    id        bigint generated by default as identity,  -- auto_increment와 동일
    item_name varchar(10),
    price     integer,
    quantity  integer,
    primary key (id)
);
```

### 대리 키 vs 자연 키

| 키 종류 | 예시 | 특징 |
|--------|------|------|
| **자연 키** | 주민번호, 이메일, 전화번호 | 비즈니스 변화에 취약 |
| **대리 키** (권장) | DB auto-increment, 시퀀스 | 비즈니스와 무관 → 변경 위험 없음 |

> 자연 키처럼 보이는 값도 비즈니스 요구사항 변화로 변경될 수 있다 (예: 주민번호 보관 금지 법 개정).  
> JPA는 모든 엔티티에 대리 키 사용을 권장. 자연 키 후보는 유니크 인덱스로 대신 관리.

## 테스트 인터페이스 기반 작성

```java
@SpringBootTest
class ItemRepositoryTest {
    @Autowired
    ItemRepository itemRepository;  // 구현체가 아닌 인터페이스에 의존

    @AfterEach
    void afterEach() {
        if (itemRepository instanceof MemoryItemRepository) {
            ((MemoryItemRepository) itemRepository).clearStore();
        }
    }
}
```

> 인터페이스를 테스트하면 구현체가 바뀌어도 같은 테스트로 검증 가능.  
> DB를 사용하는 구현체는 `clearStore()` 대신 트랜잭션 롤백으로 테스트 격리.
