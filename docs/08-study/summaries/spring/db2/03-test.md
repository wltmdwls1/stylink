# 데이터 접근 기술 - 테스트

> 스프링 DB 2편 | DB2

---

## 전체 흐름 한눈에 보기

```
테스트 격리 발전 단계

① 문제 발견
   로컬 DB(~/test)를 main/test가 공유 → 이전 테스트 데이터가 남아서 findItems() 실패

② DB 분리
   test용 별도 DB(~/testcase) 운영
   → 같은 테스트 2번 실행 시 또 실패 (데이터 누적)

③ 트랜잭션 롤백 전략
   @BeforeEach: 트랜잭션 시작
   @AfterEach:  트랜잭션 롤백
   → 테스트 후 DB 데이터 자동 제거

④ @Transactional (최종 해결)
   테스트 클래스에 @Transactional → 테스트 종료 시 자동 롤백
   (서비스/리포지토리의 @Transactional도 테스트 트랜잭션에 참여)

⑤ 임베디드 모드 DB
   외부 DB 불필요 → H2 메모리 DB (jdbc:h2:mem:db)
   → 스프링 부트: datasource 설정 없으면 자동 임베디드 모드
   → src/test/resources/schema.sql로 테이블 자동 생성
```

## 테스트 - 데이터베이스 연동

```properties
# src/main/resources/application.properties
spring.profiles.active=local
spring.datasource.url=jdbc:h2:tcp://localhost/~/test
spring.datasource.username=sa

# src/test/resources/application.properties (수정 전 — 문제!)
spring.profiles.active=test
# datasource 설정 없음 → 테스트에서 DB 접근 불가
```

```properties
# src/test/resources/application.properties (수정 후)
spring.profiles.active=test
spring.datasource.url=jdbc:h2:tcp://localhost/~/test  ← main과 동일 DB 사용
spring.datasource.username=sa
```

> **문제**: main과 test가 같은 DB를 사용 → 이전 서버 실행 때 저장한 데이터가 남아서 `findItems()` 실패.

## 테스트 - 데이터베이스 분리

```properties
# main: ~/test (서비스용)
spring.datasource.url=jdbc:h2:tcp://localhost/~/test

# test: ~/testcase (테스트 전용)
spring.datasource.url=jdbc:h2:tcp://localhost/~/testcase
```

> DB를 분리해도 같은 테스트를 2번 실행하면 실패 — 첫 번째 실행 데이터가 남아있기 때문.  
> **테스트 핵심 원칙**:
> - 테스트는 다른 테스트와 격리해야 한다.
> - 테스트는 반복해서 실행할 수 있어야 한다.

## 테스트 - 데이터 롤백 (직접 구현)

```java
@SpringBootTest
class ItemRepositoryTest {
    @Autowired ItemRepository itemRepository;

    @Autowired
    PlatformTransactionManager transactionManager;  // 스프링 부트 자동 등록
    TransactionStatus status;

    @BeforeEach
    void beforeEach() {
        status = transactionManager.getTransaction(new DefaultTransactionDefinition());
    }

    @AfterEach
    void afterEach() {
        if (itemRepository instanceof MemoryItemRepository) {
            ((MemoryItemRepository) itemRepository).clearStore();
        }
        transactionManager.rollback(status);  // 테스트 데이터 전부 롤백
    }
}
```

> 테스트 중 예외가 발생해도 트랜잭션을 커밋하지 않았으면 롤백 → 데이터 자동 제거.

## 테스트 - @Transactional

```java
@Transactional  // 이것만 추가하면 모든 테스트가 자동 롤백
@SpringBootTest
class ItemRepositoryTest {}
```

### @Transactional 테스트 동작 방식

```
1. 테스트 시작 → 트랜잭션 시작
2. 테스트 로직 실행 (INSERT, SELECT 등)
   → 트랜잭션 전파: 리포지토리/서비스의 @Transactional도 이 트랜잭션에 참여
   → 같은 트랜잭션 = 같은 커넥션 = 저장한 데이터 바로 조회 가능
3. 테스트 종료 → 자동 롤백 (커밋 X)
4. DB에 데이터 없음
```

> 일반 @Transactional은 성공 시 커밋, **테스트의 @Transactional은 항상 롤백**.  
> 테스트 메서드/클래스에 직접 붙인 경우에만 이 특수 동작이 적용된다.

### 강제 커밋 (@Commit)

```java
@Commit          // 또는 @Rollback(value = false)
@Transactional
@SpringBootTest
class ItemRepositoryTest {}
```

> DB에 데이터가 실제로 저장됐는지 눈으로 확인하고 싶을 때만 사용.

## 테스트 - 임베디드 모드 DB

외부 H2 서버 없이 JVM 메모리 안에서 H2를 실행.

### 직접 설정

```java
// @Profile("test") DataSource 빈 수동 등록
@Bean
@Profile("test")
public DataSource dataSource() {
    DriverManagerDataSource dataSource = new DriverManagerDataSource();
    dataSource.setDriverClassName("org.h2.Driver");
    dataSource.setUrl("jdbc:h2:mem:db;DB_CLOSE_DELAY=-1");
    // DB_CLOSE_DELAY=-1: 커넥션이 모두 끊겨도 DB 유지 (없으면 첫 커넥션 종료 시 DB 사라짐)
    dataSource.setUsername("sa");
    dataSource.setPassword("");
    return dataSource;
}
```

### 테이블 자동 생성 (schema.sql)

```sql
-- src/test/resources/schema.sql (스프링 부트 자동 실행)
drop table if exists item CASCADE;
create table item (
    id        bigint generated by default as identity,
    item_name varchar(10),
    price     integer,
    quantity  integer,
    primary key (id)
);
```

> 메모리 DB는 애플리케이션 시작 시 비어있으므로 `schema.sql`로 테이블을 초기화해야 한다.

## 테스트 - 스프링 부트 자동 임베디드 모드 (최종)

```properties
# src/test/resources/application.properties
spring.profiles.active=test
# spring.datasource.url=...  ← 주석 처리 (설정 없음)
# spring.datasource.username=...
logging.level.org.springframework.jdbc=debug
```

> **datasource 설정이 없으면** 스프링 부트가 임베디드 H2 DataSource를 자동 생성.  
> `schema.sql`은 그대로 동작.  
> 로그: `conn0: url=jdbc:h2:mem:{임의UUID}` (충돌 방지용 랜덤 이름)

```properties
# DB 이름 고정하려면
spring.datasource.generate-unique-name=false
# → jdbc:h2:mem:testdb 고정
```

## 테스트 설정 최종 요약

| 단계 | 방법 | 문제 |
|------|------|------|
| ① 공유 DB | main과 동일 DB | 이전 데이터 오염 |
| ② DB 분리 | ~/testcase 별도 DB | 반복 실행 시 데이터 누적 |
| ③ 롤백 직접 구현 | @BeforeEach/@AfterEach + PlatformTransactionManager | 코드 복잡 |
| ④ @Transactional | 테스트에 @Transactional → 자동 롤백 | 외부 DB 필요 |
| ⑤ 임베디드 DB | datasource 미설정 → 자동 H2 메모리 DB | **최종 권장** |

## 면접 Q&A

**Q: 테스트에서 @Transactional의 동작이 일반 코드와 다른 이유는?**
A: 스프링은 테스트 클래스/메서드에 `@Transactional`이 붙어 있을 때 특수하게 동작한다 — 테스트가 성공하든 실패하든 관계없이 종료 시 **항상 롤백**한다. 일반 프로덕션 코드의 `@Transactional`은 성공 시 커밋, 예외 시 롤백이지만, 테스트는 DB 격리가 목적이므로 항상 롤백이 기본이다. 덕분에 `@AfterEach`에서 DELETE SQL을 직접 실행하거나 트랜잭션 매니저를 주입해서 관리할 필요가 없다.

**Q: 테스트 시 임베디드 H2를 쓰는 이유와 주의점은?**
A: 임베디드 H2는 외부 DB 서버 없이 JVM 메모리 안에서 실행되므로 환경 구성이 간단하고 CI에서도 별도 인프라가 불필요하다. 스프링 부트는 `spring.datasource.url`이 없으면 자동으로 임베디드 H2 DataSource를 등록해준다. 주의점은 두 가지다. 첫째, 메모리 DB는 애플리케이션 시작 시 비어있으므로 `src/test/resources/schema.sql`에 DDL을 작성해야 한다. 둘째, 실제 운영 DB(MySQL 등)와 SQL 방언이 다를 수 있어서 임베디드 테스트가 통과해도 실제 DB에서 실패하는 경우가 있다.

**Q: @BeforeEach/@AfterEach로 트랜잭션 롤백 vs @Transactional 차이는?**
A: 결과는 같지만 편의성 차이가 있다. `@BeforeEach/@AfterEach`로 직접 구현하면 `PlatformTransactionManager`를 주입받고 `getTransaction/rollback`을 명시적으로 호출해야 한다. `@Transactional`은 이 모든 것을 한 줄로 대체하며, 테스트 실행 중 예외가 발생해도 커밋하지 않았으므로 자동 롤백된다. 단, 커밋 없는 데이터는 다른 트랜잭션에서 보이지 않으므로 `SELECT … FOR UPDATE` 같은 잠금 테스트는 주의가 필요하다.
