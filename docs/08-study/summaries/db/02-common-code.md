# 공통 코드 설계

> 데이터베이스 로드맵 | DB 설계 패턴

---

## 전체 흐름 한눈에 보기

```
하드코딩 문제 (불일치·오타·변경 어려움)
  ↓
코드값 분리 (DB에는 'ORDER', 'PAID' 같은 영문 코드 저장)
  ↓
단순 테이블 (code PK + name) → 그룹 충돌 문제
  ↓
그룹화 설계 (common_code_group + common_code_detail)
  ↓
단점: 조인 지옥(Join Hell)
  ↓
해결 1: 애플리케이션에서 코드 조회 (SQL 단순화)
  ↓
해결 2: 로컬 캐시 + TTL (DB 조회 99.99% 감소)
  ↓
ENUM vs 공통 코드 선택 (또는 하이브리드)
```

---

## 공통 코드가 필요한 이유

상태값을 문자열로 직접 저장하면 3가지 문제 발생:

| 문제 | 현상 |
|------|------|
| 데이터 불일치 | '주문완료' / '주문 완료' / 'ORDER_COMPLETE' 혼재 |
| 오타 버그 | '배송중' → '배송증' 저장돼도 DB는 모름 |
| 변경 어려움 | 수백만 건 UPDATE + 락 발생 |

해결: DB에는 코드값(`ORDER`, `PAID`)만 저장, 표시 이름은 별도 관리

## 그룹화 설계 (실무 표준)

```
common_code_group
  group_code (PK)   | group_name | use_yn
  ORDER_STATUS      | 주문상태    | Y
  MEMBER_GRADE      | 회원등급    | Y

common_code_detail
  (group_code, code) PK | name   | sort_order | use_yn
  ORDER_STATUS / ORDER  | 주문접수 | 1         | Y
  ORDER_STATUS / CANCEL | 주문취소 | 5         | Y
  PAYMENT_STATUS / CANCEL | 결제취소 | 4       | Y  ← 같은 CANCEL 코드 공존 가능
```

핵심: `(group_code, code)` 복합 PK → 다른 그룹에서 같은 코드값 사용 가능

조회 시 반드시 group_code와 code 두 필드 모두 조건에 포함:
```sql
JOIN common_code_detail c ON c.group_code = 'ORDER_STATUS' AND o.order_status = c.code
```

## 추가 속성 처리

**방법1: 컬럼 추가 (속성이 2~3개 고정일 때 권장)**
```
attr1 = 할인율(%), attr2 = 적립률 ...
그룹 테이블에 attr1_name, attr2_name으로 의미 명시
```

**방법2: EAV** → 속성이 가변적이고 많을 때. 성능 저하 주의, 뒤 챕터에서 상세 설명.

## 단점 및 해결 방안

### 문제: 조인 지옥
결제 정보 1개 조회에 비즈니스 조인 3개 + 공통 코드 조인 4개 → SQL 2배 복잡

### 해결 1: 애플리케이션에서 코드 조회
```
SQL: 코드값만 조회 (ORDER, PAID ...) → SQL 단순
애플리케이션: Map<그룹코드, Map<코드, 이름>> 으로 변환

getCodeName("ORDER_STATUS", order.orderStatus) → "주문접수"
```

단점: 추가 쿼리 필요, N+1 위험

### 해결 2: 로컬 캐시 + TTL (권장)

공통 코드 특성:
- 데이터 적음 (수백 건, ~25KB)
- 변경 드묾 (주 1~2회)
- 조회 매우 빈번 (초당 수백~수천 회)

```
TTL 60초 → 1분마다 DB 재로딩, 나머지는 메모리 조회
효과: DB 조회 12,000회 → 1회 (99.99% 감소)
```

다중 서버 동기화: 각 서버가 TTL 만료 시 자동 갱신 → 최대 1분 딜레이 (운영상 허용 가능)

> 직접 구현 금지 (동시성 버그 위험). 검증된 캐시 라이브러리 사용.

## 공통 코드 vs 애플리케이션 ENUM

| 구분 | 공통 코드 테이블 | 애플리케이션 ENUM |
|------|----------------|-----------------|
| 용도 | 단순 목록 표시 | 비즈니스 로직 분기 |
| 타입 안전성 | X (오타 위험) | O (컴파일 체크) |
| 변경 유연성 | O (DB만 수정) | X (재배포 필요) |
| 자동완성 | X | O |

### 선택 기준

```
비즈니스 로직(if문) 사용 여부?
  ├─ NO  → 공통 코드만 (은행 목록, 지역 코드 등)
  └─ YES → 표시 이름/속성 자주 변경?
            ├─ NO  → ENUM만 (성별, 고정 상수 등)
            └─ YES → 하이브리드 전략
```

### 하이브리드 전략

```java
// ENUM: 코드값 + 비즈니스 로직
enum OrderStatus { ORDER, PAID, SHIPPING, DELIVERED, CANCEL }

if (order.status == OrderStatus.PAID) { ... }  // 타입 안전

// 공통 코드 DB: 표시 이름 + 추가 속성 (운영자가 즉시 수정 가능)
getCodeName("ORDER_STATUS", status.name())  // "결제완료"
```

운영 규칙:
- 코드 추가 = 개발자 (ENUM + DB 동시 추가)
- 이름/속성 변경 = 운영자 (DB만 수정)
- ENUM ↔ DB 동기화 검증 테스트 필수

## 설계 특이점

**자연키(String) 사용**: 코드성 테이블은 그 자체로 의미가 명확 → 대리키 불필요, 가독성 유리

**외래 키 미사용**: 복합 PK 구조 때문에 참조 테이블에 불필요한 `group_code` 컬럼이 추가되어야 함. 애플리케이션(ENUM)에서 이미 검증하므로 DB FK 없이 느슨한 관계 유지.

## 면접 Q&A

**Q: 공통 코드 테이블을 그룹화 구조로 설계하는 이유는?**
A: 단순 `code + name` 구조는 도메인이 다른 테이블에서 같은 코드값(예: CANCEL)을 쓸 수 없다. `(group_code, code)` 복합 PK를 사용하면 그룹이 다르면 같은 코드값을 공존시킬 수 있고, 특정 그룹의 코드 목록만 조회하거나 그룹 단위로 활성화/비활성화도 가능하다.

**Q: 공통 코드를 ENUM 대신 DB 테이블로 관리할 때의 트레이드오프는?**
A: DB 테이블은 운영자가 배포 없이 이름/속성을 즉시 변경할 수 있는 유연성이 장점이다. 반면 애플리케이션 코드에서 문자열로 직접 사용하면 오타 위험과 타입 안전성 문제가 생긴다. 실무에서는 비즈니스 로직 분기에는 ENUM을, 표시 이름과 추가 속성 관리에는 DB 공통 코드 테이블을 함께 쓰는 하이브리드 전략을 많이 사용한다.

**Q: 공통 코드 조회 시 발생하는 조인 지옥을 어떻게 해결하나?**
A: SQL에서 공통 코드 조인을 제거하고, 애플리케이션 시작 시 또는 TTL 주기로 공통 코드를 메모리에 캐싱한다. 코드 이름이 필요할 때는 DB 조회 없이 Map에서 즉시 조회한다. TTL(예: 60초)을 설정하면 다중 서버 환경에서도 최대 1분 내에 DB 변경이 자동 반영된다.

**Q: stylink 프로젝트에서는?**
A: `OrderStatus`, `InventoryStatus`, `ReservationStatus` 등은 비즈니스 로직 분기가 핵심이므로 ENUM으로 관리하고, 화면 표시 이름이나 회원 등급별 혜택은 공통 코드 테이블에서 관리하는 하이브리드 전략이 적합하다. stylink는 현재 ENUM + `private final String description` 패턴을 사용 중 → 표시 이름 변경이 잦아지면 하이브리드로 전환 고려.
