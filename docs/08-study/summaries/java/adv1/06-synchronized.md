# 동기화 - synchronized

> 자바 고급1편 | 33페이지 | DEEP

## 전체 흐름 한눈에 보기

```
V1 (동기화 없음)
  → 문제: 두 스레드가 동시에 임계 영역 진입 → 잔액 -600원
  
V2 (synchronized 메서드)
  → 해결: 한 번에 하나의 스레드만 실행
  → 문제: 로그 출력까지 전부 잠겨서 동시 실행 범위가 불필요하게 좁음

V3 (synchronized 블럭)
  → 해결: 진짜 임계 영역만 보호, 나머지는 동시 실행 가능
  → 문제: 타임아웃·인터럽트·공정성 모두 불가
  
→ java.util.concurrent.locks.ReentrantLock 등장 (다음 챕터)
```

## V1 — 동기화 없음: 문제 발생

계좌에 잔액이 1000원 있고, 두 스레드(t1, t2)가 동시에 800원 출금을 시도한다.

출금 로직은 두 단계다.
1. 잔액(1000) ≥ 출금액(800)인지 검증
2. 통과하면 잔액에서 차감

t1이 1단계(검증)를 통과한 직후, t2도 1단계(검증)를 실행한다. 이때 t1이 아직 잔액을 차감하지 않았으므로 t2도 잔액을 1000원으로 읽는다. 결과적으로 t1, t2 둘 다 검증을 통과하고, 둘 다 800원씩 출금에 성공한다. **최종 잔액은 -600원.**

```java
public boolean withdraw(int amount) {
    if (balance < amount) return false;   // ← t1, t2 둘 다 통과
    sleep(1000);
    balance = balance - amount;           // ← 둘 다 차감, 결과 -600
    return true;
}
```

**왜 이런 일이 생기나?**  
`balance = balance - amount`는 단순해 보여도 내부적으로 3단계로 쪼개진다.
1. `balance` 값을 읽는다 (두 스레드 모두 1000을 읽음)
2. `1000 - 800 = 200` 계산
3. `balance = 200` 저장 (두 스레드 모두 200을 저장 → 한 번의 차감만 반영)

**임계 영역(Critical Section)**: 이처럼 여러 스레드가 동시에 실행하면 데이터가 깨지는 코드 구간.  
해결책은 이 구간을 **한 번에 하나의 스레드만 실행**하게 만드는 것이다.

> **volatile을 쓰면 안 되나?**  
> `volatile`은 메모리 가시성만 해결한다 — t1이 변경한 값을 t2가 즉시 볼 수 있게 해주는 것.  
> 하지만 t2가 t1의 변경된 잔액을 즉시 보더라도, t1이 **검증을 마치고 차감하기 직전**에 t2가 끼어들면 여전히 같은 문제가 생긴다.  
> 검증과 차감을 하나의 원자적 단위로 묶는 것이 핵심 — 그게 `synchronized`가 하는 일이다.

> **공유 자원 vs 지역 변수**  
> 인스턴스 필드(`balance` 같은 멤버 변수), 클래스 변수(static)는 여러 스레드가 공유한다.  
> 반면 **지역 변수는 절대 공유되지 않는다.** 각 스레드는 자신만의 스택 메모리를 갖고, 지역 변수는 거기에 저장되기 때문이다.

## V2 — synchronized 메서드: 문제 해결

```java
// synchronized 추가 → 한 번에 하나의 스레드만 실행
public synchronized boolean withdraw(int amount) {
    if (balance < amount) return false;
    sleep(1000);
    balance = balance - amount;
    return true;
}
```

**어떻게 동작하나?**  
모든 객체는 내부에 **모니터 락(monitor lock)**을 하나 가지고 있다.

```
t1 → synchronized 메서드 진입 시도 → 락 획득 → RUNNABLE 유지 → 실행
t2 → synchronized 메서드 진입 시도 → 락 없음 → BLOCKED 상태로 무한 대기
t1 → 메서드 완료 → 락 자동 반납
t2 → 자동으로 락 획득 → BLOCKED → RUNNABLE → 실행
```

실행 결과를 보면 t2가 BLOCKED 상태인 것이 보인다.
```
t1 state: TIMED_WAITING  (출금 처리 중)
t2 state: BLOCKED        (락 대기 중)
```
t1이 완료되고 나서야 t2가 검증을 시작하는데, 이때 잔액이 이미 200원이므로 t2는 검증 실패로 출금하지 못한다.

**V2의 남은 문제**: 메서드 전체가 임계 영역이 되어버린다.  
"거래 시작" 로그처럼 공유 자원을 건드리지 않는 코드도 한 번에 하나의 스레드만 실행하게 된다. → 불필요한 성능 저하.

## V3 — synchronized 블럭: 범위 최소화

```java
public boolean withdraw(int amount) {
    log("거래 시작");            // 공유 자원 안 씀 → t1, t2 동시 실행 가능

    synchronized (this) {      // ← 진짜 임계 영역만 여기부터
        if (balance < amount) return false;
        sleep(1000);
        balance = balance - amount;
    }                          // ← 여기까지

    log("거래 종료");            // 공유 자원 안 씀 → t1, t2 동시 실행 가능
    return true;
}
```

실행 결과를 보면 "거래 시작"은 t1, t2가 동시에 출력되지만, 잔액 처리는 순서대로 진행된다.
```
t1] 거래 시작: BankAccountV3
t2] 거래 시작: BankAccountV3    ← 동시 출력
t1] [검증 시작] 출금액: 800, 잔액: 1000
t2 state: BLOCKED               ← 이제서야 대기
```

**임계 영역은 꼭 필요한 최소 범위로 좁힐수록 성능이 좋아진다.**  
지금 예제에선 로그 몇 줄 차이지만, 실제로 임계 영역 밖에 DB 조회나 외부 API 호출이 있다면 성능 차이가 크다.

## V2/V3의 한계 → 다음 챕터로 이어지는 이유

`synchronized`는 편리하지만 두 가지가 불가능하다.

**무한 대기**: BLOCKED 상태가 되면 락을 얻을 때까지 끝없이 기다린다.  
웹 애플리케이션에서 고객 요청이 응답 없이 10초, 20초 기다리는 상황이 생길 수 있다. "3초 기다렸다 안 되면 포기"같은 타임아웃이 불가능하고, 인터럽트도 걸 수 없다.

**공정성 없음**: 락이 반납됐을 때 대기 중인 스레드 중 누가 다음 락을 가져갈지 보장이 없다.  
특정 스레드가 계속 후순위로 밀려 아주 오래 실행되지 못하는 기아(starvation) 현상이 생길 수 있다.

이 두 문제를 해결하기 위해 자바 1.5에서 `ReentrantLock`이 등장한다 → **07-concurrent-lock.md** 참고.

## 면접 Q&A

**Q: synchronized와 volatile의 차이는?**  
A: `volatile`은 메모리 가시성만 해결한다. 한 스레드가 변경한 값을 다른 스레드가 즉시 볼 수 있게 해주는 것. 반면 `synchronized`는 원자성까지 보장한다. 검증 → 차감처럼 여러 단계가 한 덩어리로 실행되어야 할 때는 `synchronized`가 필요하다.

**Q: synchronized 메서드와 블럭의 차이는?**  
A: 메서드에 붙이면 메서드 전체가 임계 영역이 된다. 블럭으로 쓰면 공유 자원을 건드리는 부분만 보호하고 나머지는 동시에 실행할 수 있다. 블럭이 성능상 더 유리하다.

**Q: BLOCKED 상태란?**  
A: `synchronized` 메서드나 블럭에 진입하려다 락을 못 얻은 스레드가 대기하는 상태. CPU 스케줄링에 포함되지 않고, 타임아웃도 없고, 인터럽트도 걸 수 없다. 락이 반납되는 순간 자동으로 깨어나 락 획득을 시도한다.

**Q: synchronized의 단점과 대안은?**  
A: 무한 대기(타임아웃 없음)와 공정성 보장 안 됨이 단점. 자바 1.5에서 추가된 `ReentrantLock`으로 이 단점들을 해결한다.

**Q: final 필드는 멀티스레드에서 안전한가?**  
A: 안전하다. 동시성 문제의 본질은 "공유 자원이 중간에 변경되는 것"이다. `final` 필드는 아무도 값을 바꿀 수 없으니, 여러 스레드가 동시에 읽어도 항상 같은 값이 나온다.

## stylink 실전 적용

`InventoryItem`의 상태를 `AVAILABLE → RESERVED`로 바꾸는 코드가 대표적인 임계 영역이다.  
두 고객이 동시에 같은 재고를 예약하려 하면, 둘 다 "AVAILABLE 확인 → RESERVED로 변경" 사이에 끼어들 수 있다.

단순한 경우엔 `synchronized`로 시작해볼 수 있지만, 실제 서비스에선 단일 JVM을 넘어서는 경우가 많아 DB 레벨의 낙관적 락(`@Version`) 또는 비관적 락(`SELECT FOR UPDATE`)을 쓰는 게 일반적이다. `synchronized`는 그 원리를 이해하는 기반이 된다.
